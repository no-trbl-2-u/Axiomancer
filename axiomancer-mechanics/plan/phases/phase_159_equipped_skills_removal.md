## Goal

Finish the half-done Phase 99 migration by **removing** the deprecated
`equippedSkills` field entirely. Per T (2026-06-20): "`equippedSkills` is no
longer relevant; the access surface is learned skills only." Do **not** bless
the field as a compatibility surface. Goal: stop every audit re-discovering it.

## Decisions (made upfront)

- **D1 — Remove, don't bless.** `equippedSkills` is deleted from `Character`
  (`src/Character/types.ts`), `CreateCharacterOptions`, `CharacterPreset`, all
  preset records, the Tuning loadout builder, and the CLI dev-tools.
- **D2 — No version bump.** Removing a field does not require a new save
  version. `GAME_STATE_VERSION` stays 10. The existing v7→v8 migration already
  merges legacy `equippedSkills` into `knownSkills`; that merge is the
  "save-migration path" the brief asks for. The migration now reads the legacy
  field off a locally-typed legacy payload (`LegacyPlayerV7`) and **does not**
  write it back — post-migration `Character` has no such field.
- **D3 — `devEquipSkills` deleted.** It is CLI-internal (not in the locked
  `src/index.ts` barrel / public-surface fixture), so deletion is safe. The CLI
  "Unlock skills (DEPRECATED)" menu entry already routes to a no-op explainer
  stub; that stub stays (informs players the gate was removed) but its
  `equip-skills` action no longer calls `devEquipSkills`. `devMaxOut` drops its
  `devEquipSkills` call (all skills already unlocked via `devUnlockSkills`).
- **D4 — Test fixtures drop the field.** Every `*.test.ts` passing
  `equippedSkills` to `createCharacter` or asserting on `player.equippedSkills`
  is updated to remove the field / assertion. The `phase99-migration` and
  `phase99-unlocked-access` tests are rewritten to assert the merge result on
  `knownSkills` only (no `equippedSkills` read-back).
