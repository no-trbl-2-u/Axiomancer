## Headline findings

1. **Dice have no values.** `CombatManaDie` = `{id, color, state, temporary}` —
   no pips exist, so zero of the 88 cards can read, threshold, or scale with a
   die. Only 3 cards carry any dice verb (all `grant_permanent_wild_die`); the
   spec-promised `die-manipulation` / `x-die-interaction` classes have zero
   implementations; the dragged `dieId` is a dead parameter.
2. **The effect libraries mostly target a removed combat system.** Only ~5
   payload channels are read by the live HP engine; 18/71 debuffs and 47/54
   buffs are complete no-ops; enemy debuffs on the player are ~100% cosmetic
   except DoTs (stun/petrify/charm/silence on the player did nothing); all 125
   resistedBy/resistDR entries are dead; the stance×action×tier proc table is
   dead code; 8 of 11 registry combos are dead and 2 more have unreachable
   ingredients.
3. **The card number was in three different broken units.** `bottomDamagePreview`
   summed the REMOVED pressure-track credit (intensity × CONTROL_HARD_MULT 6…);
   `READ_STATUS_MULT` rewrote intensity after application (a provable no-op
   below intensity 3, while the UI advertised ×1.34/×0.75 of the lifetime
   total with different rounding); `projectCardImpact` omitted the resistance
   and VULNERABLE factors execution applies. Runtime repro: eternal-regress
   previews "12" → enemy receives confusion i1 + slow i1 + 3 HP.

## Adversarially confirmed mechanical claims (27/27 — none refuted)

### No card reads a die value — dice have no values to read (complaint #1 root cause)
CombatManaDie carries only {id, color, state, temporary}; the face bag is 6 COLOR faces (heart/body/mind/wild/x/x), no pips. Therefore 0 of 88 cards can read, threshold, or scale with a rolled value. Every die is a binary spend-to-power token; the only per-die texture is engine-global (color-match +3 flat, read multiplier), identical for every card. Interaction-class census (via real projection): 88 cards = direct-dot 22, direct-control 22, buff-self 21, direct-damage 10, stat-debuff 7, defend 5, befriend 1; cards with ANY dice-verb text: 3 (all grant_permanent_wild_die, cards.library.ts:1811,1902,2055); cards reading a die face/value: 0; X-die-interaction cards: 0.

*Evidence:* axiomancer-mechanics/src/Combat/combat.encounter.types.ts:46-52; src/Combat/combat.dice.ts:32-34 (COMBAT_DIE_FACES); src/Combat/combat.engine.ts:597-872 (playBottomAction — die used only as gate at 613-615, read mult 623-670, color-match 627/648); verb-class counts from tsx run over cardLibrary + toCombatCard

### Card text lies: 'Costs 1 {color} die' but the engine accepts any non-X die (feeds complaint #3)
bottomActionText for status cards is templated as `Costs 1 ${cardStanceColor(skill)} die`, but playBottomAction's only gate is drafted.state==='available' && color!=='x' — it never calls combatDieCanPower, so a mind die powers a heart card fine (it just forfeits the +3 match bonus and may read disadvantage). combatDieCanPower is imported into the engine at line 42 and only re-exported at 1553; it is never invoked in any play path. The printed cost text does not match engine behavior.

*Evidence:* src/Combat/combat.cards.ts:264; src/Combat/combat.engine.ts:613-615 (actual gate), 42 + 1553 (combatDieCanPower imported but never called in engine)

### resolveCardDieCost advertises a 0/1/2-die RPS cost that is never charged (dead pricing model)
resolveCardDieCost (advantage → 0 dice free, disadvantage → 2 dice) implements Spec 25 §4.8, but no play path charges variable die cost — playBottomAction always consumes exactly the one drafted die (or refreshes it via the variety loop). The function's only consumer is cardDieCostPreview, rendered by the CLI at combat.cli.ts:352, so the UI-facing 'cost' preview describes a pricing system that does not exist. Another printed-number-vs-engine mismatch in the complaint #3 family.

*Evidence:* src/Combat/combat.engine.ts:195-201, 1415-1417; src/CLI/combat.cli.ts:352; contrast actual spend at combat.engine.ts:827-832; specs/25-hazard-pattern-combat.md:299-301,639

### The dieId a player drags onto a card is silently ignored by the engine
playCombatCard threads dieId into playBottomAction, whose parameter is named _dieId and never read — the engine always uses the turn's drafted die regardless of which die the caller specifies. Under the current single-drafted-die model this is redundant-but-harmless, but it means the 'drag a die onto the card' interaction is theater at the engine layer: the drag target cannot matter, and any future multi-die pool would silently misbehave.

*Evidence:* src/Combat/combat.engine.ts:601 (_dieId: string | undefined, no reads), 444-469 (playCombatCard passes dieId through), 1216 (resolveCombatPhase passes play.dieId)

### Spec-promised dice card categories have zero implementations: die-manipulation, x-die-interaction, temporary dice
Spec 25 defines card categories `die-manipulation` (refresh/recast/convert dice) and `x-die-interaction` (enable spending X dice), and §7.4 describes temporary dice 'created by card effects'. In the library: 0 cards in either category (the only dice mechanic is grant_permanent_wild_die ×3); no code path anywhere flips an X die to available except a full reroll of it; and the CombatManaDie.temporary field is never set true by any combat code (all constructors hard-code temporary:false) — a dead field. The X-die comment in combat.dice.ts ('unless a card enables X-die interaction') promises a hook that does not exist.

*Evidence:* specs/25-hazard-pattern-combat.md:384,387,448,153; src/Combat/combat.dice.ts:31-33,149-153; src/Combat/combat.encounter.types.ts:50-51; grep 'temporary: true' over src (only Hazard hits); specialMechanics census: grep kind: in cards.library.ts

### All 88 cards share four template strings for their die interaction text — no card has unique dice behavior to print
topActionText/bottomActionText are generated from verbClass via a handful of ternary templates in toCombatCard; no card contributes bespoke action text, because no card HAS bespoke die behavior for text to describe. This is why the hand reads as boring: mechanically, every dot card is 'Full damage-over-time — impact ~N. Costs 1 die' with only N varying, and N itself is the impact-track preview (perRound×intensity with caps/multipliers), not the HP the enemy will actually lose — a second contributor to the complaint-#3 'number on the card' mismatch (the printed ~preview uses CONTROL_HARD_MULT=6/CONTROL_SOFT_MULT=4 track weights and IMPACT_INTENSITY_CAP=3, while actual applied intensity is read-scaled and uncapped to 10).

*Evidence:* src/Combat/combat.cards.ts:246-264 (templates), 107-143 (effectImpact weights + IMPACT_INTENSITY_CAP), 193-213 (bottomDamagePreview); actual applied intensity path src/Combat/combat.engine.ts:658-670

### Proc table (baseChance 0.05-0.18) is dead code — statuses never come from procs in the live game
rollForCombatEffects/applyProcOutcome/getEligibleTriggers have no callers outside tests and barrel re-exports; the Hazard-Pattern engine (combat.engine.ts) never imports them, and axiomancer-mobile has zero references. ### Soft-control magnitude is imperceptible vs normal enemies: -6% enemy damage per roll-penalty point
The 25 soft-control-only debuffs convert to weakenMult = 1 - 0.06 x penalty (floor 0.4) and deny at cumulative penalty >=8 (needs e.g. confusion -5 + fear -4 stacked simultaneously) or 3 DISTINCT control effects (DISRUPT). A landed fear (-4) vs a level-2 normal enemy shaves ~24% of a ~9 HP threat hit = ~2 HP saved against a 150 HP player — invisible in play. It only becomes tangible vs bosses (threat budget x1.5, escalation up to x2.0 at x1.6 rate). rollModifier is also explicitly non-intensity-scaling (types.ts:96), so re-landing fear does nothing except refresh duration — stacking a control feels dead.

*Evidence:* combat.engine.ts:104-106 (THREAT_WEAKEN_PER_ROLL 0.06, THREAT_DENY_AT 8, floor 0.4), 920-922, 131-149 (escalation); threatDamageBudget combat.threat.ts:121-130 → L2 normal ~5 x THREAT_DAMAGE_SCALE 1.7 ≈ 9 HP; types.ts:96-99

### READ_STATUS_MULT rescales a just-applied intensity AFTER application — printed effect points can differ from what sticks
On a powered card play the engine snapshots pre-card intensities, lets the skill apply its effect, then rewrites the enemy's intensity to round(prior + delta x statusMult) for advantage/disadvantage reads. A card previewing 'intensity 2' can therefore land as 1 or 3 depending on the hidden-stance read, and Math.max(1, ...) guarantees at least 1 even on a lost read. Combined with finding 4 (inert payloads) this is the effects-side mechanism for complaint 3: the number the card shows is not the number (or behavior) the enemy ends up with. Note also two different default intensities exist: EFFECT_BASE_PROC_INTENSITY=2 on the (dead) proc path vs intensityDelta 1 default on the live skill path.

*Evidence:* src/Combat/combat.engine.ts:633,651-670; src/Game/game-mechanics.constants.ts:159; src/Cards/skill.engine.ts:570-608 (intensityOverride ?? 1)

### bottomDamagePreview is in dead 'pressure-track impact' units but is surfaced to the player as damage/effect points
bottomDamagePreview sums effectImpact(), whose units are the REMOVED two-track win model's credit: hard control = intensity x CONTROL_HARD_MULT(6) + duration credit, soft control = intensity x 4, DoT = perRound x min(intensity, IMPACT_INTENSITY_CAP=3) with duration ignored. The card text templates print it as 'impact ~N' and, on gold cards, literally as '~N damage'; the mobile rewards overlay renders it as '+N damage' (dot) or '+N effect' (other). Runtime proof (seeded engine run): eternal-regress previews 12 ('+12 effect') but a powered play gives the enemy debuff_confusion int=1 + debuff_slow int=1 (2 effect points) and only 3 HP chip; slippery-slope previews 6 ('+6 damage') but actually deals 3 HP immediate + bleed int=2 dur=3 = 18 lifetime DoT (per-round tick 6). ### Read-scaling honesty gap: UI scales the displayed DoT TOTAL, engine rounds the INTENSITY — advertised advantage/disadvantage numbers are wrong, and are no-ops at low intensity
The mobile face/detail/armed-pill computes read-scaled status numbers as Math.round(total x READ_STATUS_MULT[read]) (e.g. Slippery Slope 18 total -> pill 'adv 24 / even 18 / dis 14'; detail readNote quotes the same). The engine instead scales only the landed intensity delta: Math.round(prior + delta x statusMult). Runtime proof: advantage play lands bleed int=3 dur=3 -> actual lifetime 27 (UI said 24); disadvantage play lands int=2 unchanged -> actual 18 (UI said 14, i.e. the advertised penalty NEVER happens because Math.round(2 x 0.75)=2). Corollary: for every intensity-1 status card, both advantage (round(1.34)=1) and disadvantage (round(0.75)=1) are complete no-ops even though the UI advertises x1.34/x0.75 — this also directly feeds complaint #1 ('no interaction with the dice'): the marquee die-read x status interaction does not exist below intensity 3.

*Evidence:* Engine: axiomancer-mechanics/src/Combat/combat.engine.ts:159-161 (READ_STATUS_MULT), :658-670 (intensity-delta rounding: 'Math.round(prior + delta * statusMult)'). UI: axiomancer-mobile/state/presenters/combat-encounter.engine.ts:781-789 (armedReadValue: round(statusBase x mult)), :755-758 (diePill triplet), :707 (detail readNote '≈ round(total x 1.34)'). Repro output: 'FACE armed pill triplet = adv 24 / even 18 / dis 14' vs 'ACTUAL (advantage) bleed int=3, pending 27' and 'ACTUAL (disadvantage) bleed int=2, pending 18'.

### Strike preview (projectCardImpact) omits damage resistance and VULNERABLE that execution applies
projectCardImpact computes base = calculateSkillDamage(state.player, skill) WITHOUT the target argument, so calculateDamageResistance (which subtracts the enemy's full body/mind/heart stat, floor 1) never runs, and it multiplies by READ_DAMAGE_MULT only — no vulnMult. Preview overstates against tanky foes and understates against VULNERABLE-marked foes. Note: mobile currently renders strike faces number-less ('small direct hit') and no mobile call site of projectCardImpact was found, so this is a latent divergence in the exported 'UI preview' selector (also inherited by projectSiphonHeal at combat.engine.ts:1544-1550).

*Evidence:* Preview: axiomancer-mechanics/src/Combat/combat.engine.ts:1460-1474 (no target arg at :1469, no vulnMult at :1471). ### Three contradictory numbers for the same card across one play flow
For Slippery Slope the player can see: hand face '18 over 3 turns' (dpr 3 x int 2 x turns 3 — this one IS honest on an even read: pending DoT = 18), rewards-overlay '+6 damage' (bottomDamagePreview track units), and after landing, the enemy status chip showing intensity '2' (chips() renders ae.intensity). ### dice-interaction
The owner's complaint #1 is mechanically confirmed: a combat die has NO numeric value to read (CombatManaDie = {id, color, state, temporary} — color faces heart/body/mind/wild/x only), so zero of the 88 library cards read, gamble on, or scale with a die face; a die is a binary spend-to-power token whose only texture is an engine-global color check applied identically to every card (+3 flat color-match, RPS read multipliers). ### doctrine-alignment
The card and effect libraries are written for a game that no longer exists: card previews and ~half the effect payload vocabulary are denominated in the removed Pressure-Track model or in payload fields the HP-model engine never reads. All three owner complaints verify. (1) Dice: Spec 25 §6 promises die-manipulation/card-draw/amplifier/persistent-enchant/x-die-interaction card classes and §4.8 a stance-keyed die-cost economy — the shipped 86-card pool has zero cards in any of those classes, the RPS die-cost function is dead code, and dice are a pick-1-of-2 color for a hidden read plus a uniform power slot. (2) Effects: statuses always land (Phase 80 removed resist rolls) but most are hollow — the engine consumes only DoT payloads, negative rollModifier (as an invisible -6%/pt threat weaken), skipTurn, and damageTakenMult>1; every statModifier/defenseModifier/advantageModifier on 40+ debuffs and ~80% of self-buffs is inert, and the entire 2026-07-03 "status-stacking" drop leans on six statuses (doubt, sensory_null, isolated, overextended, clarity, resolute) whose payload flags have no engine consumer at all. (3) The card-number bug is real and threefold: bottomDamagePreview/"impact ~N" is in phantom pressure units, READ_STATUS_MULT silently rescales landed intensity after the number is shown, and strike/synergy damage is quartered by DIRECT_DAMAGE_WEIGHT after the preview. ## Design judgment

Winner: **prior-art** (spine of the synthesis).

Scores:

DICE-FIRST — fun 9/10: pip-reading, parity forks, visible ±2 read-shift and chain-rerolls make every single play a read (strongest direct answer to "no interaction with the dice"). feasibility 5/10: self-rated L rewrite of playBottomAction plus a global basePower rebase (DIRECT_DAMAGE_WEIGHT deletion), a brand-new RNG surface (value roll per die), and re-pinning every hermetic suite — the largest blast radius and the only proposal that adds randomness rather than reading existing state. identity 9/10: the fallacy names become mechanical puns on cheating the roll (liars-paradox inverts bands, false-dilemmas-fork forces val to 1 or 6) — best per-card flavor of the three. mobile 7/10: pips on dice are universally legible and the band table is clean, but 8 keywords plus per-card odd/even/exact riders push face density. complaints 9/10: #1 head-on, #3 solved by construction (resolvePoweredOutcome), #2 solid but subordinate to dice.
STATUS-ENGINE — fun 7/10: the three-line build-threshold-detonate arc is a real crescendo and thresholds visibly rewrite the telegraph, but most per-play verbs collapse to "+2 pips of a line," risking a new monotony in new units. feasibility 7/10: no die-shape change and it reuses the rupture/weaken paths, but it re-points ~50 cards wholesale, bans 100+ effects from combat, and requires retuning fight length from 2-4 to 4-6 rounds — a big balance bet. identity 6/10: three generic tracks flatten per-card philosophy into routing; the reactions are evocative but only three exist. mobile 9/10: three notched meters plus one exact pre-play number is the cleanest phone read of any proposal. complaints 7/10: #2 and #3 excellent; #1 thinnest — dice remain color tokens whose only new job is routing, which the owner may still read as "no interaction."
PRIOR-ART — fun 8/10: four second-reads on the same roll (Resonance tally, Reserve ripening, Omen, Fate) plus a visible bank-or-burn genuinely unsolves the 15-line greedy draft, and card-printed threshold/dieBonus/fate lines give per-card dice text. feasibility 9/10: almost everything is S/M wiring of already-authored surfaces — the 12 dead 2026-07-03 payload fields, carriedDie, rerollSpentDice, the grant_permanent_wild_die dispatch pattern — and its P1 phase fixes all three complaints with zero new mechanics; this is also exactly the fix priority the effect-depth audit itself prescribed. identity 7/10: the fallacy=threshold / paradox=fate law is good and False Dilemma (the die you burn names the door you close) is the best single card in any proposal, but the long tail leans on mapping rules. mobile 7/10: explicit KB-derived guards (status cap 5, glossary, Inevitable fast-forward, scripted first fight), though four new dice systems need careful visual hierarchy. complaints 9/10: #1 via card-printed dice lines + tally/reserve/omen/fate, #2 via the audit-prescribed wiring + Spirit-Island telegraph ladder, #3 via single-source projection + CI preview==applied invariant.
VERDICT: prior-art wins on feasibility-weighted fun and complaint coverage — it is the only proposal an engineer can ship incrementally with each phase green, and its dice answer is deterministic (KB law: randomness that nullifies declared intent is resented). Grafts taken: dice-first's by-construction single resolver (engine applies the projection struct, not a parallel path), its dieId/temporary-die/preserve verbs and several card identities; status-engine's consuming REACT detonations on the mechanicDamage path, its struck-through telegraph rendering, and its exact-number-at-draft preview discipline.
