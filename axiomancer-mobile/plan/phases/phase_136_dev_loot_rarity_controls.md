# Phase 136 — Dev loot rarity controls

## Outcome

Fix the dev inventory tools so rarity evidence matches mechanics truth:

- **POPULATE** should provide the deterministic registry-backed inventory load: common/base items and unique items. It must not pretend to manufacture uncommon/rare procedural affix gear from the template registry.
- Add two new dev menu buttons:
  - **LOOT UNCOMMON** — generate and add a real uncommon equipment drop.
  - **LOOT RARE** — generate and add a real rare equipment drop.

This gives the Kid and the visual smoke path a clean way to inspect all four item presentations after Phase 135:

- common/plain via POPULATE
- unique/red-outline via POPULATE
- uncommon/green-shine via LOOT UNCOMMON
- rare/blue-shine via LOOT RARE

## Source / user decision

T direct steering, 2026-06-17:

> Have it a phase where it provides "common" and "unique" since uncommon and rare are generated at drop time. But then also, in the same phase, add 2 new buttons "loot uncommon" and "loot rare".

## Mechanics truth to respect

- Uncommon and rare equipment are generated at **drop time**, not as static registry rows to be dumped by POPULATE.
- Common/base equipment and unique equipment come from registries/templates and are legitimate POPULATE content.
- Unique items are fixed/non-procedural and should stay unique by explicit rarity tagging.
- Do not fake rarity by hand-editing arbitrary template objects except where the engine API requires a rarity option for real drop generation.

## Decisions made upfront — DO NOT ASK

- Keep POPULATE as the broad inventory/debug load, but make its label/copy honest: it provides common/base + unique registry gear and consumables; uncommon/rare are generated through separate drop buttons.
- Add two separate buttons, not a dropdown:
  - `LOOT UNCOMMON`
  - `LOOT RARE`
- Buttons belong under `/dev` → **INVENTORY & ITEM TOOLS**, near POPULATE and ADD ITEM BY ID.
- Use engine drop-generation truth if available (`dropItem` / current mechanics API), with deterministic seeds if the API supports it.
- If the engine drop API does not expose a direct rarity request, create a tiny mobile-side dev adapter that calls the engine repeatedly with bounded attempts until the requested rarity appears; do not ship an unbounded loop.
- Add visible result text: item name + rarity + affix count/source, e.g. `looted uncommon · Keen Iron Knife · 1 affix`.
- Add graceful failure text if a requested rarity cannot be generated.
- Production stays inert through `isDevToolsEnabled()` gates.
- Do not alter actual gameplay loot tables for this phase.

## Implementation units

1. **Clarify POPULATE behavior**
   - Files likely involved:
     - `components/DebugPopulateAllItems.tsx`
     - `state/actions.ts`
     - `components/__tests__/DebugPopulateAllItems.test.tsx`
   - Update copy from “one of every item in the game” to the stricter truth:
     - common/base registry gear
     - unique registry gear
     - consumables
     - uncommon/rare are generated by the new loot buttons
   - Ensure POPULATE still tags unique templates as `rarity: 'unique'`.
   - Do not attempt to add uncommon/rare by mutating static templates.

2. **Add dev loot action(s)**
   - Likely new module:
     - `state/dev/loot-rarity.ts`
   - Expose actions through `state/actions.ts` / `useGameActions()`:
     - `lootUncommonItem(): LootRarityResult`
     - `lootRareItem(): LootRarityResult`
   - Result shape should include:
     - `added: boolean`
     - `rarity: 'uncommon' | 'rare'`
     - `name: string | null`
     - `affixCount: number | null`
     - `reason: string | null`
   - Count affixes from structured fields for reporting only:
     - `prefixName` / `prefixId`
     - `suffixName` / `suffixId`
   - Expected counts:
     - uncommon = 1
     - rare = 2

3. **Add UI buttons**
   - Likely new component:
     - `components/DebugLootRarityButtons.tsx`
   - Mount in:
     - `components/dev/DevToolsSections.tsx`
   - Place under **INVENTORY & ITEM TOOLS** near POPULATE.
   - Buttons:
     - `LOOT UNCOMMON`
     - `LOOT RARE`
   - Visible last-result text must include success/failure and generated item.

4. **Tests**
   - Add or extend:
     - `components/__tests__/DebugPopulateAllItems.test.tsx`
     - `components/__tests__/DebugLootRarityButtons.test.tsx`
     - `state/dev/__tests__/loot-rarity.test.ts` if helper is pure/testable
   - Required assertions:
     - POPULATE copy no longer claims uncommon/rare static registry dump.
     - POPULATE adds common/base + unique registry content and preserves unique rarity.
     - LOOT UNCOMMON calls action and surfaces uncommon success with 1 affix.
     - LOOT RARE calls action and surfaces rare success with 2 affixes.
     - Failure path renders visible reason.
     - Dev tools are gated outside dev profile.
